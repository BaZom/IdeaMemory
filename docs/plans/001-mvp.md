## Shared definition of done and workflow

For every task: approved scope implemented by Claude; concrete criteria satisfied; relevant tests/checks executed and results reported; no unrelated changes; documentation/ADR updates where behavior changes; actual diff reviewed by Codex; accepted blocking findings resolved; final CI passed. Human owns merge and release. No claim that `make check` proves physical Safari behavior, AI quality or hosted security without those checks.

Level 2: concise plan and criteria, Claude implementation/tests, Codex review, CI, human merge. Level 3 additionally requires a concrete motivation, alternatives/tradeoffs and explicit approval of meaningful changes; accepted decisions cover routine details. Level 1 documentation corrections need only focused checks. All production/destructive operations retain explicit human gates.

## Task 001 — Project bootstrap

**Brief status:** Finalized for Claude Code handoff on 2026-10-11. **Implementation approved by the human on 2026-10-11 for Task 001 only**, as defined in this brief, including deferring Riverpod until Task 002. The approval excludes Task 002, Supabase/OpenAI configuration, cloud resources, deployment, merging, commits, pushes and Git remote changes, each of which needs separate authorization. No approval of Tasks 002–008 or proposed ADRs is implied.

**Goal:** A new contributor can start a Flutter Web shell that checks a FastAPI health endpoint and run genuine, reproducible repository validation.

**Classification:** Level 3 because this establishes the initial stack and dependencies. The requested stack is already the planning baseline; this task introduces no new product architecture. Use the shared review workflow above.

**Scope:** Minimal Flutter Web/Material 3 shell, FastAPI package, typed HTTP boundary, health connectivity UI, dependency/toolchain pins, meaningful tests, `make check`, GitHub Actions configuration, public local configuration examples, ignore rules, manifest/icons and verified development instructions.

**Non-goals:** Authentication, Supabase configuration/SDKs, database schema/migrations, idea CRUD, OpenAI configuration/SDKs, native builds, hosting/deployment, production resources, offline caching, generic architecture frameworks and empty future feature modules. No provider credentials are needed.

**Dependencies:** Explicit implementation instruction from the human. Remote CI additionally requires an authorized GitHub repository and push; a physical iPhone is needed for device verification. Those external checks may remain pending while local implementation proceeds, but must not be reported as passed.

### Implementation choices for this handoff

- Flutter Web only, Material 3, neutral internal package names unrelated to the working product name. Keep branding in display/configuration values.
- Use built-in Flutter state for this one interaction. Defer Riverpod evaluation to Task 002, when shared authentication/session state provides a concrete need. No code generation, routing framework or extra state framework in this task.
- Use one small HTTP client boundary (Dart `http` package recommended) so widget tests can control results without a real server. Keep request handling out of widget build methods; no generic repository/use-case hierarchy.
- Python FastAPI/Uvicorn, pytest with an appropriate HTTP test client, Ruff, mypy, and standard package build tooling. Use a `src` package layout and an isolated virtual environment.
- Inspect available versions and verify compatibility against official documentation before pinning. Document exact Flutter/Dart/Python versions actually tested. Ordinary compatible version selection within this list does not require another approval.
- Commit the Flutter application lockfile; maintain reproducible Python runtime/dev dependency pins, including transitive dependencies, and document the frozen installation procedure used by CI. Do not introduce a package/monorepo framework solely for bootstrap.
- Install project dependencies in isolated project environments. Respect tool permission prompts; report missing SDKs instead of silently replacing global installations. Docker and Supabase CLI are not prerequisites for this task.

### Concrete behavior

`GET /health` returns HTTP 200 with JSON `{"status":"ok"}`. It is a public process-liveness check with no external calls, credentials, database checks, or sensitive configuration/version disclosure. It is not proof that future provider integrations are ready.

Flutter reads public `API_BASE_URL` configuration and requests `/health` on initial load. Show a small “Connection check” view with loading, connected, and failure states. Failure has an explicit retry button; disable overlapping retries. A non-200 response, invalid response body, network failure or bounded timeout produces a recoverable failure state, not success. Dispose/cancel handling must prevent updating a removed widget. No automatic polling or retry loop.

Suggested local ports are Flutter 3000 and API 8000. Document the exact verified run commands, public build-time configuration and an explicit development CORS origin allowlist. The frontend must honor configured URLs rather than always using localhost. Do not use wildcard CORS to hide configuration errors. Server startup must work without Supabase/OpenAI variables.

Provide ordinary web manifest/icons, responsive layout and labeled controls. Do not add a service worker or claim offline support. A phone cannot reach the developer machine through its own localhost; document LAN setup for a non-sensitive smoke check and distinguish it from HTTPS/installability verification in Task 008. Do not create a public tunnel or hosted environment without authorization.

## Task 002 — Authentication and private access

**Goal:** Invited users authenticate and access only their identity-bound API context.

**Scope:** Supabase email OTP and invite restriction; session refresh/logout; verified API identity; local Supabase configuration; initial RLS/grant testing with isolated fixtures; user-token Data API/Storage integration boundary. Prove isolation using test-only records, without prematurely building the idea schema.

**Non-goals:** Custom auth, social login, profile feature, roles hierarchy, full domain schema or production provisioning.

**Dependencies:** 001 and ADR 002 approval including browser session tradeoff.

**Expected components:** Flutter auth/session state, API auth dependency/data client, local Supabase config and test fixtures, CI integration job.

**Acceptance criteria:** Invited login/refresh/logout works; wrong/expired/malformed signatures, issuer/audience and forged ownership fail; unauthorized signup fails at provider; protected endpoint derives subject; two local users cannot read/write each other's fixture rows/objects directly or through API; logout/account switch clears private state; signing-key refresh fails safely.

**Tests:** Auth dependency unit tests; local Supabase auth/RLS/grant/Storage integration tests with two users; direct-provider bypass tests; widget session tests; manual email/session flow.

**Risks:** RLS bypass via service credentials, insecure JWT decoding, open signup, client cache leakage, key rotation.

**Definition of done:** Shared definition plus demonstrated API and provider isolation; no production auth setup without separate authorization.

## Task 003 — Manual ideas

**Goal:** A user reviews, saves, browses, edits and deletes a manual idea.

**Scope:** First idea/source migrations, nullable category, tags/notes/location, saved/done status; source-free manual save; basic collection/detail UI; version conflicts and retry-safe save; owned CRUD; source text preservation where supplied.

**Non-goals:** URL fetching, images, AI, advanced search, custom categories, complete future schema.

**Dependencies:** 002; approval of domain defaults and schema/invariants.

**Expected components:** Ideas feature, API ideas/sources schemas and data operations, SQL constraints/RLS/save RPC, local integration fixtures.

**Acceptance criteria:** Nonblank title suffices; optional fields remain optional; only explicit confirmation persists; editing does not lose notes/original text; failed save retains draft; retry cannot duplicate the same operation; stale edit returns conflict; delete removes from collection/retrieval; cross-user IDs and owner changes fail; category/status constraints also hold through direct Data API writes.

**Tests:** CRUD/validation/conflict/retry tests, two-user RLS and foreign-key tests, fresh/upgrade migration checks, Flutter review/edit/delete flow and manual iPhone entry.

**Risks:** Lost updates, duplicate retries, cross-owner references, AI-oriented schema overdesign.

**Definition of done:** Shared definition plus complete manual end-to-end flow with AI unconfigured.

## Task 004 — URL capture

**Goal:** A pasted URL becomes a user-reviewed idea retaining the original link, even when extraction fails.

**Scope:** Safe bounded metadata fetching, source provenance, duplicate warning within account, editable review, optional structured AI enrichment through the small adapter and quota boundary. Establish atomic AI usage limits before real calls. Can be reviewed as safe metadata/fallback slice followed by advisory enrichment slice, each with full UI/API tests.

**Non-goals:** Login scraping, JS browser rendering, downloading previews/videos, imports, arbitrary model tools.

**Dependencies:** 003; ADR 003/privacy/spend approval before AI use.

**Expected components:** Capture UI, URL extraction module, source persistence, AI adapter, usage ledger migrations/tests.

**Acceptance criteria:** Exact original URL persists separately from normalized duplicate key; failed/restricted/non-HTML fetch can save manually; metadata is advisory; owner-scoped duplicate warning does not merge; SSRF controls cover DNS rebinding and every redirect; limits enforced during streaming/decompression; invalid AI output/refusal does not overwrite draft; quotas remain effective under concurrent requests.

**Tests:** Mock HTTP resolver/transport tests for public/private/mixed IPv4/IPv6, redirects, credentials, nonstandard ports, time/size limits, rebinding; metadata fixtures; prompt-injection/refusal/schema cases; source save/ownership tests; manual real restricted-platform fallback with non-sensitive data.

**Risks:** SSRF, remote tracking, incorrect metadata, provider spend and content retention.

**Definition of done:** Shared definition plus security tests and successful no-AI URL fallback.

## Task 005 — Screenshot capture

**Goal:** A valid screenshot can be privately uploaded, interpreted, reviewed, saved and reopened as its original.

**Scope:** Bounded image validation/upload, private Storage, upload bookkeeping and atomic attachment, multimodal adapter, editable preview/fallback, authorized display, cancellation/expiry/deletion and idempotent operator reconciliation.

**Non-goals:** Video, public assets, asynchronous AI jobs, queue/scheduler infrastructure, automatic album imports.

**Dependencies:** 004; approved retention and storage lifecycle; real AI only within approved budget/privacy.

**Expected components:** Capture/source UI and API, image validator, Storage policies, upload migrations/RPC, cleanup command and runbook.

**Acceptance criteria:** Validate bytes/type/decoded size; reject unsupported/oversized inputs clearly; original remains private and recoverable; AI failure still permits image-backed manual save after successful upload; foreign/expired/deleting upload cannot attach; concurrent save/cleanup is safe; repeated delete/reconcile is idempotent; cancelled/abandoned content is removed within documented operator cadence; failed removal stays visibly pending for retry; two users cannot access each other's objects or mint links.

**Tests:** Image fixture and oversized/bomb tests, local private Storage authorization, orphan/partial-failure/race tests, quota tests, widget review/fallback tests, physical iPhone screenshot picker and original reopen. Record a small opt-in live model evaluation separately from mocked CI.

**Risks:** Private image exposure, memory exhaustion, orphaned objects, provider image retention, signed-link leakage, Safari formats.

**Definition of done:** Shared definition plus verified cleanup/retry runbook and original-image preservation.

## Task 007 — Conversational rediscovery

**Goal:** The assistant recommends owned saved ideas and refines them using active-session context.

**Scope:** Owner-scoped retrieval, bounded context, structured responses, ID/evidence validation, canonical item references, follow-ups, missing-fact/no-match behavior and provider failure fallback.

**Non-goals:** Persistent chat, generic internet recommendations, live prices/hours/weather, autonomous tools, embeddings without evidence.

**Dependencies:** 006; ADR 003 approval and accepted session-only behavior.

**Expected components:** Chat UI/state, recommendation module, AI adapter, evaluation fixtures and tests.

**Acceptance criteria:** Recommendations reference currently owned candidate ideas; deleted/foreign/invented IDs are rejected; “less expensive” does not invent price facts; inferences are labeled; empty/no-match cases are honest; follow-ups use only bounded current-session context; logout clears context; injection cannot invoke tools or broaden ownership; limit/outage yields owned search fallback and clear status. At least 80% of answerable representative cases retrieve a relevant item in top 5, or investigate baseline query defects before requesting architecture expansion.

**Tests:** At least 20 curated mixed-language cases including no match and follow-ups; adversarial saved text/chat; stale/deleted IDs; two-user isolation; cost limits; mocked provider failure/schema tests; approved live usefulness evaluation separately recorded.

**Risks:** Hallucination despite valid IDs, prompt injection, poor small-collection relevance, excessive context/spend.

**Definition of done:** Shared definition plus documented retrieval/grounding results and no silent generic fallback.
