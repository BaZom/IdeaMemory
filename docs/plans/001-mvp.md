### Concrete behavior

`GET /health` returns HTTP 200 with JSON `{"status":"ok"}`. It is a public process-liveness check with no external calls, credentials, database checks, or sensitive configuration/version disclosure. It is not proof that future provider integrations are ready.

Flutter reads public `API_BASE_URL` configuration and requests `/health` on initial load. Show a small “Connection check” view with loading, connected, and failure states. Failure has an explicit retry button; disable overlapping retries. A non-200 response, invalid response body, network failure or bounded timeout produces a recoverable failure state, not success. Dispose/cancel handling must prevent updating a removed widget. No automatic polling or retry loop.

Suggested local ports are Flutter 3000 and API 8000. Document the exact verified run commands, public build-time configuration and an explicit development CORS origin allowlist. The frontend must honor configured URLs rather than always using localhost. Do not use wildcard CORS to hide configuration errors. Server startup must work without Supabase/OpenAI variables.

Provide ordinary web manifest/icons, responsive layout and labeled controls. Do not add a service worker or claim offline support. A phone cannot reach the developer machine through its own localhost; document LAN setup for a non-sensitive smoke check and distinguish it from HTTPS/installability verification in Task 008. ### Proposed decisions included in task approval

1. **Email OTP, operator-provisioned accounts, local-first.** Disable unrestricted and anonymous signup at Supabase itself. Flutter requests OTP with `shouldCreateUser: false`; this client flag alone is not the security control. Provision synthetic local users using the supported Auth admin API, outside normal application requests. Use the local email inbox to obtain codes; configure the template to send a code, not only a magic link. No external SMTP account is needed for this task.
2. **Direct Supabase Auth in Flutter.** Use `supabase_flutter` for token storage/refresh and auth events. Keep session state in a small built-in notifier/controller; Riverpod is still deferred unless implementation demonstrates a concrete reason to introduce it. Do not add a second token store, custom refresh timer, routing framework or state-management dependency.
3. **Online verification for the first backend auth slice.** Validate each access token with the configured Supabase Auth user endpoint (`get_user(jwt)` semantics) before accepting identity. This delegates signature/key verification to the configured provider and avoids a separate JWKS cache or local signing secret. It adds a network dependency and latency; authenticated requests fail closed during provider outages. A future change to locally verified asymmetric JWTs requires evidence and a reviewed plan, not two verifier modes now.
4. **User-token database/storage access.** Normal requests forward the already-validated user's token plus public project key. Never use service/admin credentials as a fallback. Privileged credentials are limited to local provisioning and test-fixture setup/cleanup.
5. **Managed browser persistence.** Restore sessions across reloads using the SDK; browser script access to stored tokens is an acknowledged tradeoff. Do not add third-party scripts or render untrusted HTML; keep auth tokens/codes out of logs, URLs and error text. No claim of instantaneous access-token revocation on logout.

### Concrete user experience and API contract

On startup show an auth-restoration loading state. Signed-out UI asks for email, then the email code; support change-email, resend with an appropriate cooldown, invalid/expired-code feedback, and retry for provider failure. Do not expose raw provider errors or claim whether an address is invited. No public signup form. Respect provider rate limits and prevent duplicate submits.

After verification, show a simple signed-in screen with the verified user's identifier, protected-API status and Sign out. Preserve the public Task 001 health diagnostic as a separate diagnostic; it must not acquire an authentication requirement or contact Supabase. No collection UI yet.

`GET /api/v1/me` accepts `Authorization: Bearer <access-token>` and returns `200 {"user_id":"<verified UUID>"}` with `Cache-Control: no-store`. It accepts no owner parameter and does not trust local Flutter session data as server identity. Missing/malformed/invalid/expired tokens return 401 with a consistent safe error envelope and bearer challenge. A bounded timeout/unavailable provider returns 503; never return a fabricated user or treat an outage as successful authentication. Use request IDs without sensitive token/body logging.

The verification endpoint and project key come only from trusted server settings; do not follow a token-supplied issuer/JWKS URL or redirects to arbitrary origins. Use the supported provider operation for cryptographic verification; enforce expected issuer, authenticated audience/role, expiry and valid UUID subject, and match the subject to the provider-returned user. Any claim inspection must not become a decode-only authentication path. Reject admin/service tokens, wrong-project tokens and non-user identities. Confirm the pinned provider's verification guarantees and cover the application requirements with explicit tests. Use HTTPS for any future hosted provider; localhost/local isolated test networking is the only development exception.

Share transport connections if useful, but never mutate a shared SDK client's user session/default authorization header per request. Concurrent A/B requests must carry their own tokens, preventing identity leakage across requests. Keep server access tokens request-local.

Flutter attaches the current SDK token to the protected request. On authentication rejection, allow at most one SDK-mediated refresh/retry; no infinite loop or custom token refresh subsystem. On provider outage retain an honest retry state rather than destroying a valid local session. On logout, clear private UI immediately, invoke SDK sign-out, and report remote-signout failure if necessary. Cancel or ignore delayed responses from the previous session using a session generation/identity check; `mounted` alone does not prevent A's response showing after B signs in. Dispose subscriptions and clients according to their ownership.

Document the selected sign-out scope and the provider's token-expiry behavior. Clearing the browser session is not proof that a copied JWT immediately becomes unusable. Do not build a custom revocation ledger for this task.

**Acceptance criteria:** Exact original URL persists separately from normalized duplicate key; failed/restricted/non-HTML fetch can save manually; metadata is advisory; owner-scoped duplicate warning does not merge; SSRF controls cover DNS rebinding and every redirect; limits enforced during streaming/decompression; invalid AI output/refusal does not overwrite draft; quotas remain effective under concurrent requests.

**Tests:** Mock HTTP resolver/transport tests for public/private/mixed IPv4/IPv6, redirects, credentials, nonstandard ports, time/size limits, rebinding; metadata fixtures; prompt-injection/refusal/schema cases; source save/ownership tests; manual real restricted-platform fallback with non-sensitive data.

**Risks:** SSRF, remote tracking, incorrect metadata, provider spend and content retention.

**Definition of done:** Shared definition plus security tests and successful no-AI URL fallback.

## Task 005 — Screenshot capture

**Goal:** A valid screenshot can be privately uploaded, interpreted, reviewed, saved and reopened as its original.

**Scope:** Bounded image validation/upload, private Storage, upload bookkeeping and atomic attachment, multimodal adapter, editable preview/fallback, authorized display, cancellation/expiry/deletion and idempotent operator reconciliation.

**Non-goals:** Video, public assets, asynchronous AI jobs, queue/scheduler infrastructure, automatic album imports.

**Dependencies:** 004; approved retention and storage lifecycle; real AI only within approved budget/privacy.

**Expected components:** Capture/source UI and API, image validator, Storage policies, upload migrations/RPC, cleanup command and runbook.

**Acceptance criteria:** Validate bytes/type/decoded size; reject unsupported/oversized inputs clearly; original remains private and recoverable; AI failure still permits image-backed manual save after successful upload; foreign/expired/deleting upload cannot attach; concurrent save/cleanup is safe; repeated delete/reconcile is idempotent; cancelled/abandoned content is removed within documented operator cadence; failed removal stays visibly pending for retry; two users cannot access each other's objects or mint links.

**Tests:** Image fixture and oversized/bomb tests, local private Storage authorization, orphan/partial-failure/race tests, quota tests, widget review/fallback tests, physical iPhone screenshot picker and original reopen. Record a small opt-in live model evaluation separately from mocked CI.

**Risks:** Private image exposure, memory exhaustion, orphaned objects, provider image retention, signed-link leakage, Safari formats.

**Definition of done:** Shared definition plus verified cleanup/retry runbook and original-image preservation.

## Task 006 — Collection experience

**Goal:** Users quickly find and inspect saved ideas on mobile.

**Scope:** Bounded paginated browse, PostgreSQL full-text search and category/status filters, empty/loading/error states, source display, accessible mobile refinements and measured indexes.

**Non-goals:** Semantic/vector search, recommendation feed, custom taxonomy, native navigation.

**Dependencies:** 003–005.

**Expected components:** Collection/detail UI, list/search API, search/index migration, representative fixtures.

**Acceptance criteria:** Search covers canonical title/description/tags/notes/location; uncategorized ideas remain discoverable; pagination stable without duplicate items under unchanged data; all filters preserve ownership; source links/images work; keyboard/back/loading/empty states are usable on iPhone; query latency measured on a proposed 1,000-idea synthetic collection and documented (provisional target p95 under 300 ms for database query, excluding network).

**Tests:** Search/filter/pagination/ownership integration, query plan/timing record, mobile widget accessibility and physical Safari checks.

**Risks:** Weak multilingual recall, inappropriate indexes, stale signed URLs, inaccessible controls.

**Definition of done:** Shared definition plus representative retrieval fixtures reusable by Task 007.

## Task 007 — Conversational rediscovery

**Goal:** The assistant recommends owned saved ideas and refines them using active-session context.

**Scope:** Owner-scoped retrieval, bounded context, structured responses, ID/evidence validation, canonical item references, follow-ups, missing-fact/no-match behavior and provider failure fallback.

**Non-goals:** Persistent chat, generic internet recommendations, live prices/hours/weather, autonomous tools, embeddings without evidence.

**Dependencies:** 006; ADR 003 approval and accepted session-only behavior.

**Expected components:** Chat UI/state, recommendation module, AI adapter, evaluation fixtures and tests.

**Acceptance criteria:** Recommendations reference currently owned candidate ideas; deleted/foreign/invented IDs are rejected; “less expensive” does not invent price facts; inferences are labeled; empty/no-match cases are honest; follow-ups use only bounded current-session context; logout clears context; injection cannot invoke tools or broaden ownership; limit/outage yields owned search fallback and clear status. At least 80% of answerable representative cases retrieve a relevant item in top 5, or investigate baseline query defects before requesting architecture expansion.

**Tests:** At least 20 curated mixed-language cases including no match and follow-ups; adversarial saved text/chat; stale/deleted IDs; two-user isolation; cost limits; mocked provider failure/schema tests; approved live usefulness evaluation separately recorded.

**Risks:** Hallucination despite valid IDs, prompt injection, poor small-collection relevance, excessive context/spend.

**Definition of done:** Shared definition plus documented retrieval/grounding results and no silent generic fallback.

## Task 008 — PoC hardening and deployment

**Goal:** The complete capture-to-rediscovery workflow operates safely on an explicitly approved pilot environment.

**Scope:** Full physical Safari/PWA and accessibility checks; auth/security regression; failure/performance/cost checks; privacy/disclosure review; tested backup/restore/export/account deletion; CI finalization; hosting decision and human-triggered release. Split readiness verification from provisioning/release so the final action requires concrete approval.

**Non-goals:** Public commercial launch, HA fleet, enterprise compliance tooling, new features or unapproved infrastructure.

**Dependencies:** 001–007; owner-approved hosting/regions/ceiling and explicit deployment/release authorization.

**Expected components:** Only necessary fixes, CI/deploy config, environment setup, operational/privacy documentation, release verification record.

**Acceptance criteria:** All R1–R9 release gates evidenced; iPhone uploads/keyboard/back/install/update/logout pass; API/Data API/Storage isolation verified in hosted configuration; AI-down capture works; quotas and cleanup tested; restore includes files and respects deletion; export is usable; invitations wait for privacy/retention procedures; rollback is exercised or safely rehearsed against actual artifacts/schema; operator records approved release revision and smoke checks.

**Tests:** Canonical checks, hosted synthetic-account smoke/isolation, real device end-to-end, constrained failure injection, restore/export/deletion rehearsal and release/rollback verification.

**Risks:** Environment drift, migration data loss, missing objects in backup, provider auto-deployment bypass, unexpected costs.

**Definition of done:** Shared definition plus human-authorized release and recorded operational evidence. If approval is absent, deliver readiness findings and stop before provisioning/deployment.
