## Architecture

```text
 Flutter web app (phone-first, later installable)
        │  HTTPS, the user's own access token
        ▼
 FastAPI service ── verifies the token with Supabase Auth on every request
        │  acts as that user (no admin key)            │ phase 3+, server only
        ▼                                              ▼
 Supabase: Postgres with row-level security      AI provider (approved model,
 (spaces, members, memories, plans), Auth,       minimal text, no account data)
 Storage (phase 4)
```

- **Your memory is yours; spaces see suggestions.** Memories keep one owner (as today). Suggesting one to a space creates a link (memory, space); members of that space can read that memory’s card while the link exists and add their own votes, answers and notes; they never see your other memories and can’t edit yours. The database enforces it (row-level security on ownership and membership, plus column grants); the API also filters by the verified user.
- **Your answers are yours.** Votes, “I’m in” answers and notes are stored per member; only you can change your own; others see a vote only after they have answered.
- **Business rules live in the API**, so the app stays a display layer: what the nudge suggests, what is “worth knowing”, when a plan becomes history.
- **Schema changes** are forward migrations in `supabase/migrations/`; existing data is kept.
- **Original text** saved with a memory is stored separately and never changed.
- **Tokens signed with Supabase’s shared legacy secret are refused**, so a hosted project must use asymmetric signing keys.

## Technical decision per feature

| Feature (task) | Decision |
| --- | --- |
| Memories (1.1) | Extend the existing `ideas` table: kinds (travel → trip, film-series → film, recipe → food, product → other), one `note` (description + notes merged), `who_for` (first names; empty = just me), `told_by`, `season`, `weekend_only`, `link_url`, `event_start`/`event_end`, `cost`, `needs_booking`. All optional except the title. Details in [slice 1.1](slices/1.1-memory-model-and-look.md). |
| My memory (1.1) | Search runs in the database over the user’s own rows (title, note, who, location, link title, tags); browse rows are plain filters; shelves are computed from dates. No extra tables. |
| Suggest (1.8) | Rule-based in the API: *Fits now* from event dates, season, weekend, duration and context; the rest under *Later*; every item carries a short reason; today’s pick is the best fit. |
| Plans (1.7) | A `plans` table in the memory’s space: memory reference (same owner enforced by the database), day, optional time, reminder choice, where, people (names), a short checklist, what to bring. A plan is active while its day is today or later; at most one active plan per memory (checked by the API). Past plans stay as rows and show as “planned before”. |
| Reminders (1.7, M2) | In the app first (Planned); real notifications come with the native app (M2). |
| Spaces (M3) | `spaces` (name, type: two or group) and `space_members` (space, user, role owner/member); `space_ideas` (space, memory, suggested_by, created_at), insertable only by the memory’s owner who is a member. RLS: a memory is readable by its owner and by members of a space it is suggested to. *Keep in my memory* inserts a new memory owned by the caller with `who` = the suggester. Joining via an unguessable, revocable invite token checked in a security-definer function that only adds the caller. Up to 8 members. |
| Who’d join (M3) | Group members mark *I’d join* per idea (one row per member and idea); an idea is ready when enough would join (2, or its minimum); partners have no votes. |
| Plan together (M3) | `plan_answers` (plan, member, in/maybe/out), `plan_day_options` + votes, `plan_todos.assignee`, `plan_notes` (short text, author). Updates by polling first (no realtime service). Guest link: an unguessable token showing a read-only plan card; guests give a name and an answer, no account; the owner can turn it off. |
| Every week (M3) | `regular_days` (space, kind fixed/open, title, weekday, time, place, min people, decide time; up to 3 per space) and `regular_answers` (day, date, member, in/out). A scheduled job on the server sends the question and the go/no-go; answers via the app or a guest link. Date night is a regular day in a partner space with no minimum; picking an idea plans it for that evening. |
| Paste a link (1.4) | The server fetches the page: http(s) only, no private or local addresses (checked after DNS resolution and on every redirect), small size and time limits, no cookies. Reads the page title, Open Graph data and schema.org event dates. The app never fetches pages itself. |
| Fill it in (1.6) | One server-side AI call per save with the link text and your note; the answer must fit a fixed schema (kind, moods, tags, dates) and is shown as suggestions you confirm. Off switch and budget limit; the app works without it. |
| Ask your memory (M4) | Retrieval over the current space’s memories only (database search, embeddings if needed), then one AI call that may only use the retrieved memories and must cite them. If nothing matches it says so. |
| Screenshots (1.6) | Private Storage bucket with the same space rules; deleting a memory deletes its image. |
