### Accepted decisions, amended for self-service signup

1. **Self-service username/password signup and sign-in, local-first.** Trim and lowercase usernames; accept 3–30 characters from `a-z`, `0-9`, `.`, `_`, `-`, starting with a letter or number. Map to `<username>@users.invalid` internally for Supabase Auth; do not collect a real email address. Use managed password signup/sign-in with a minimum 8-character signup password. Enable signup, disable email confirmation and keep anonymous sign-in disabled. Signup returns a usable session immediately; sign-in never creates an account. No code entry, inbox step, verification link or account recovery is required for this MVP. Password storage/checking stays with Supabase Auth. Operator provisioning is optional for fixtures only.
2. **Direct Supabase Auth in Flutter.** Use `supabase_flutter` for token storage/refresh and auth events. Keep session state in a small built-in notifier/controller; Riverpod is still deferred unless implementation demonstrates a concrete reason to introduce it. Do not add a second token store, custom refresh timer, routing framework or state-management dependency.
3. **Online verification for the first backend auth slice.** Validate each access token with the configured Supabase Auth user endpoint (`get_user(jwt)` semantics) before accepting identity. This delegates signature/key verification to the configured provider and avoids a separate JWKS cache or local signing secret. It adds a network dependency and latency; authenticated requests fail closed during provider outages. A future change to locally verified asymmetric JWTs requires evidence and a reviewed plan, not two verifier modes now.
4. **User-token database/storage access.** Normal requests forward the already-validated user's token plus public project key. Never use service/admin credentials as a fallback. Privileged credentials are limited to local provisioning and test-fixture setup/cleanup.
5. **Managed browser persistence.** Restore sessions across reloads using the SDK; browser script access to stored tokens is an acknowledged tradeoff. Do not add third-party scripts or render untrusted HTML; keep auth tokens/passwords out of logs, URLs and error text. No claim of instantaneous access-token revocation on logout.

### Concrete user experience and API contract

On startup show an auth-restoration loading state. Signed-out UI exposes clearly labeled Sign up and Sign in choices with username and password fields. Validate usernames and signup password length, prevent duplicate submits, respect provider rate limits and allow retry after network/provider failures. Switching modes must not submit accidentally. Wrong-password and unknown-username sign-in use the same neutral error. Duplicate signup reports a taken username without changing that account's password or creating a second identity.

After successful signup or sign-in, show the username, server-verified user identifier, protected-API status and Sign out. Preserve the public Task 001 health diagnostic as a separate diagnostic; it must not acquire an authentication requirement or contact Supabase. No collection UI yet.

`GET /api/v1/me` accepts `Authorization: Bearer <access-token>` and returns `200 {"user_id":"<verified UUID>"}` with `Cache-Control: no-store`. It accepts no owner parameter and does not trust local Flutter session data as server identity. Missing/malformed/invalid/expired tokens return 401 with a consistent safe error envelope and bearer challenge. A bounded timeout/unavailable provider returns 503; never return a fabricated user or treat an outage as successful authentication. Use request IDs without sensitive token/body logging.

The verification endpoint and project key come only from trusted server settings; do not follow a token-supplied issuer/JWKS URL or redirects to arbitrary origins. Use the supported provider operation for cryptographic verification; enforce expected issuer, authenticated audience/role, expiry and valid UUID subject, and match the subject to the provider-returned user. Any claim inspection must not become a decode-only authentication path. Reject admin/service tokens, wrong-project tokens and non-user identities. Confirm the pinned provider's verification guarantees and cover the application requirements with explicit tests. Use HTTPS for any future hosted provider; localhost/local isolated test networking is the only development exception.

Share transport connections if useful, but never mutate a shared SDK client's user session/default authorization header per request. Concurrent A/B requests must carry their own tokens, preventing identity leakage across requests. Keep server access tokens request-local.

Flutter attaches the current SDK token to the protected request. On authentication rejection, allow at most one SDK-mediated refresh/retry; no infinite loop or custom token refresh subsystem. On provider outage retain an honest retry state rather than destroying a valid local session. On logout, clear private UI immediately, invoke SDK sign-out, and report remote-signout failure if necessary. Cancel or ignore delayed responses from the previous session using a session generation/identity check; `mounted` alone does not prevent A's response showing after B signs in. Dispose subscriptions and clients according to their ownership.

Document the selected sign-out scope and the provider's token-expiry behavior. Clearing the browser session is not proof that a copied JWT immediately becomes unusable. Do not build a custom revocation ledger for this task.

### Proposed Task 003 behavior package

### Data and validation contract

Use SQL migrations under `supabase/migrations/`. Use UUID primary keys, UTC timestamps and explicit constraints/grants/RLS. Avoid adding unused columns for future URL/image/AI features.

| Field | Task 003 rule |
| --- | --- |
| `title` | Required, trim outer whitespace, 1–200 characters after trimming; reject all-whitespace |
| `description`, `notes` | Nullable, maximum 10,000 characters each; blank optional canonical fields normalize to null |
| `location` | Nullable user text, maximum 300 characters; no geocoding or inference |
| `category` | Null or one of the keys above |
| `tags` | Default empty array; at most 20 distinct tags, each 1–50 characters after trimming; reject invalid entries/oversized input |
| `status` | `saved` or `done`, default `saved` |
| `original_text` | Optional on create only, 1–20,000 characters with at least one non-whitespace character; preserve supplied text exactly, including whitespace and line breaks |
| Server fields | `id`, `owner_id`, `created_at`, `updated_at`, integer `version` starting at 1; client cannot choose owner, timestamps or version on create |

### API contract

All routes require the current bearer identity, use `Cache-Control: no-store`, derive owner from verified identity and reuse safe error handling. IDs are UUIDs. Missing/foreign-owned resources both return the same 404 shape. Never expose provider errors, SQL or submitted field values in responses/logs.

An `Idea` response contains `id`, canonical fields, `created_at`, `updated_at`, `version` and `sources`. Each source contains `id`, `kind`, `original_text`, `created_at`; owner is not a client-editable property. List entries use the same canonical fields/server fields but omit full sources; detail/create/edit return the full idea.

| Method/path | Request | Success and relevant errors |
| --- | --- | --- |
| `POST /api/v1/ideas` | Canonical fields plus optional `original_text`; required UUID `Idempotency-Key` header | 201 full idea on initial create; 200 same idea on a valid replay; 409 key/payload mismatch or replay after that idea was deleted |
| `GET /api/v1/ideas` | `limit` default 20, range 1–100; optional opaque cursor | 200 `{items: [...], next_cursor: string or null}`; 422 malformed/unsupported cursor |
| `GET /api/v1/ideas/{id}` | No owner parameter | 200 full idea; 404 absent/foreign |
| `PATCH /api/v1/ideas/{id}` | Positive `expected_version` plus at least one editable canonical field; omitted fields unchanged, null clears nullable fields | 200 updated idea; 409 stale version; 422 invalid or immutable fields |
| `DELETE /api/v1/ideas/{id}` | Positive `expected_version` query parameter | 204 when deleted; 409 stale version; 404 absent/foreign, including a repeated successful delete |

Use keyset pagination against the last returned creation timestamp/UUID. Cursor includes only versioned paging state, never credentials; validate it strictly, and always reapply the authenticated owner predicate independently. No offset pagination or full-table client download. New inserts need not appear until collection refresh; pagination must not repeat rows with equal timestamps.

On a delete timeout, the client may re-fetch; 404 confirms the idea is no longer accessible and is treated as removed locally. For PATCH timeout, re-fetch to reconcile version/current values while retaining local edits; do not blindly retry as a new overwrite. Explain a 409 in ordinary user language, not raw database details.

### Transactions, retries and authorization

Creation of idea, optional source and retry record is one transaction through a narrowly scoped security-invoker RPC using the user's token. Derive ownership from `auth.uid()` inside the database too; do not accept an authoritative owner argument. Conditional version matching and update/delete happen atomically, not as separate read-then-write requests. Successful edits increment version and advance server-controlled `updated_at`; failed/conflicting operations make no changes. Ownership and creation identity are immutable.

Use a small owner-scoped creation-retry record with a unique `(owner_id, operation_key)`, canonical request fingerprint, resulting idea ID and database expiry (24 hours). Do not retain full request bodies or duplicate source content in this record. Concurrent identical creates must return one idea; same key with different normalized content returns 409. Replays return the current owned idea without reapplying fields. If it was deleted, return 409 and never resurrect it during the retry window; retry metadata must therefore survive idea deletion until expiry. Expired keys may be reused as new operations; document this bound. Clean expired records opportunistically during creation or with a bounded local maintenance operation; no scheduler/queue required.

The client generates one key per submitted create operation and keeps the key and submitted payload for ambiguous retries. After a timeout it must resolve/retry that operation before sending an edited payload as a new create; do not silently generate a second key on every tap. A definitive validation failure may return to editing with a new operation. Never reuse another account's draft/key.

RLS must constrain SELECT/INSERT/UPDATE/DELETE with owner checks on both existing and resulting rows. Explicitly revoke anonymous access and public execution of mutation functions; grant only required authenticated capabilities. Remember that security-invoker functions use caller table privileges: an RPC wrapper alone does not prevent direct table access. Enforce ownership, immutable fields, field constraints and source integrity in database policies/constraints/triggers as appropriate, and test direct Data API writes. Do not solve privilege issues by quietly changing the RPC to security-definer. Document the concrete grants and ensure retry-record manipulation cannot grant access to another user's idea or overwrite canonical content.

Preserve Task 002's user-scoped transport, bounded timeouts, redirect rejection and auth retry limits. CRUD requests need CORS methods and `Authorization`, `Content-Type`, `Idempotency-Key`; unrelated origins remain denied. Never construct provider table paths or filter expressions directly from arbitrary client text.
